# 3.0.0 运行时选型与能耗目标

> 日期：2026-10-21
> 状态：决策记录（运行时不变）+ 分期计划（未实施）
> 触发：讨论「3.0.0 换 CEF / Tauri / 原生」，首要目标被确定为**能耗与常驻内存**

---

## 1. 结论

**3.0.0 不更换应用运行时**：继续用 Electron 承载窗口与渲染层，把 3.0 定义成「内核进程化 + 空闲预算 + 渲染层能耗」三件事。CEF、Tauri、原生三条路线的问题不是"能不能做"，而是**它们换掉的不是当前的痛点，却要重写最贵的资产**。

判定依据按投入产出排序：

| 事实 | 数值（2026-10-21 本仓库） | 对选型的含义 |
|---|---|---|
| 主进程规模 | 966 个 TS 文件、约 35.0 万行（非测试） | 任何换宿主方案都是主进程全量重写 |
| Electron 耦合面 | 164 个文件 `import 'electron'`；`session.` 1,308、`BrowserWindow` 259、`Tray` 211、`WebContentsView` 96、`powerMonitor` 82、`screen` 40、`globalShortcut` 12 | 耦合集中在 shell（窗口/托盘/快捷键）与网络会话，恰恰是 Electron 替我们兜住的部分 |
| 原生模块 | `packages/tuff-native` 21,418 行 Rust/ObjC，全部 N-API | 离开 Node（Tauri）就无处挂载，必须重做成宿主侧；见 [`native-rust-runtime-migration-prd`](../../plan-prd/03-features/native-rust-runtime-migration-prd.md) §2 的 TCC/签名结论 |
| 验证资产 | 1,679 个测试文件 + 一整套 CDP 探针（`apps/core-app/scripts/coreapp-*`） | 换壳等于重做验收体系；CDP 是当前唯一能自动验收打包界面的通道 |
| 目标平台 | macOS arm64/x64、Windows nsis、Linux | 原生路线要么三份 UI，要么砍两平台；Tauri 的 Linux 侧是 WebKitGTK，同一份 CSS 三个引擎 |
| 现场内存 | 开发态实例 8 个 Electron 进程共 1,016 MB，其中**主进程 414 MB**、GPU/渲染 248+121 MB | 最大单块就是主进程，那是内核问题，不是壳的问题 |

## 2. 三条候选路线为什么不选

- **CEF**：把 Electron 已经提供的「Chromium + Node + 三平台打包 + 自动更新 + 签名公证」全部退回自建，Chromium 合流负担一点不减。仓库内的 [`electron-browser-feasibility-survey-2026-10-17`](./electron-browser-feasibility-survey-2026-10-17.md) 已定界：通用浏览器才需要 CEF / Chromium fork（Brave 从 Muon 推翻重建就是这样付过学费），垂直工作台用 `WebContentsView` 就是正解，而内嵌浏览器工作台已经交付。收益≈0，成本≈主进程全量。
- **Tauri 2**：渲染层可复用，但主进程 35 万行要用 Rust 重写，或挂 sidecar Node —— 变成两套运行时，常驻内存反而更高；21.4k 行 N-API 原生模块在 WKWebView 进程里没有 Node 可挂；`session`/代理/快照冻结/CDP 探针全部重做；Linux 侧 WebKitGTK 让 tuffex 的视觉验收多一条通道。它能省的是安装包里的 Chromium，而当前抱怨的是运行时能耗。
- **原生（Tern 路线）**：Tern 可行有三个前提 —— macOS-only、产品文本中心（终端/编辑器）、自建渲染引擎（`stencil_ui`/`stencil_css`/`stencil_gfx` 一套自研 DOM/CSS/Metal 合成，外加 `tern shot/record/trace` 自建工具链）。Tuff 的护城河是「三平台 + 集成面广 + JS 插件 + 内嵌浏览器」，原生路线把这四条一起削掉，成本以年计。

复核记录：`/Applications/Tern.app` 只有 `Contents/MacOS/tern`（145 MB，arm64），无 `Frameworks`，`otool -L` 仅系统框架（AppKit/WebKit/JavaScriptCore/Metal/CoreText/ScreenCaptureKit/CoreData/CloudKit/ServiceManagement），无 `libswiftCore`；`strings` 中 30 处 `electron` 全部来自文件类型图标表（`dev-electron`、`md-electron_framework`），`TAURI_INTERNALS` 为 0；Info.plist 0.9.5、最低 macOS 13。即：不是 Electron，不是 Tauri，是 Rust + AppKit 外壳 + 自研 UI 引擎 + WKWebView 只承载网页 pane。

## 3. 3.0.0 的定义

三件事，按收益顺序：

### Phase 0 — 基线（先量后改）

在 mac-work 上装当前正式包，采三组数：冷启动到 CoreBox 可交互、空闲 10 分钟能耗（`powermetrics --samplers tasks` 与 Activity Monitor 的 Energy Impact 各取一次）、按进程常驻内存（`app.getAppMetrics()` 探针，复用 `observability` 模块）。没有基线不开工。

### Phase 1 — 内核进程化

把文件/应用索引、搜索、正文与向量索引、扫描与回填搬进**同一个 bundle 内的 `utilityProcess`**（不是独立 CLI：同一签名身份才能继承 TCC，见 native PRD §2）。主进程只做路由与窗口。收益：主进程最大的一块内存搬走；扫描/回填不再与 UI 抢主线程；崩溃隔离。

### Phase 2 — 空闲预算

审计 15 个 `setInterval` 使用点与 82 处 `powerMonitor`，建立 idle 状态机：CoreBox 关闭、窗口隐藏、系统空闲时，索引/向量/OCR/AI 全部降到 0 Hz；托盘常驻只保留事件驱动。

### Phase 3 — 渲染层能耗

58 处 `requestAnimationFrame` 与 tuffex 的 refraction/backdrop 表面：窗口隐藏或面板不可见时必须 0 帧；用 CDP 统计帧数与合成层数做验收（已有先例：`perf(tuffex): stop refraction surfaces from stalling large panels`）。

### Phase 4 — 常驻内存

WebContentsView 标签的 LRU 与快照冻结（已交付）+ 面板懒加载 + 索引进程 RSS 上限。

## 4. 不做什么

- 不为 3.0.0 引入第二套 UI 运行时，不在本轮评估 CEF/Tauri 的实现。
- 不把 native 能力拆成外部 sidecar 二进制（TCC/签名/公证成本，见 native PRD §2）。
- 不把 3.0 当作版本号重启：版本线随第一个内核化 PR 一起走发布脚本。

## 5. 可逆的保留项

唯一低成本的试水，将来若追求原生手感：**只给 CoreBox 做一个原生轻壳**（Raycast 式，只读 kernel RPC，面板仍留 Web 层）。它失败只丢一个壳，不影响 3.0 主线。前提是 Phase 1 把内核抽干净——这也是为什么 Phase 1 优先。
