## 2. 实测：索引为什么这么大（2026-10-20）

测法：对两个 profile 的 `search-index.db` 做 APFS 克隆（`cp -c`），用 `dbstat` 按表和索引汇总。

| | 正式版（只索引文件名） | dev（开过正文索引） |
| --- | --- | --- |
| 文件大小 | 1,926 MB | 7,271 MB，其中空闲页 1,208 MB |
| 收录文件 | 65,642 | 58,814 |
| `keyword_mappings` 及其 5 个索引 | 1,788 MB（93%） | 1,534 MB |
| FTS（内容表加倒排） | 75 MB | 2,076 MB |
| `files` | 12 MB | 1,346 MB，其中正文 1,308 MB |
| `embeddings` | 0 | 745 MB，46,196 行 JSON，每行约 16 KB |
| `file_extensions` | 7 MB | 316 MB，其中 `content_chunks` 290 MB |

只索引名字时每个文件约 29 KB，几乎全花在关键词上：每个文件约 49 行，每行用完整路径（平均 108 字节）作 `item_id`，`(provider, item, keyword)` 和 `(provider, item)` 两个索引又各存一遍路径。按来源拆分 321 万行（脚本把每行与所属文件的文件名、祖先目录比对）：

| 来源 | 行数占比 | 说明 |
| --- | --- | --- |
| 文件名的 n-gram | 32.5% | 只在精确、前缀和 FTS 都零命中时才读，且只取 8 个种子 × LIMIT 80、无排序 |
| 不在文件名里的 n-gram | 22.3% | 来自类型标签：`code`、`typescript` 作为别名进入 n-gram 来源 |
| 祖先目录分词 | 15.7% | `users`、`talexdreamsoul` 各 65,742 行，即每个文件一行 |
| 路径短语 | 13.2% | 包括把整条路径当成一个关键词，只有查询等于整串时才命中 |
| 文件名分词 | 9.2% | |
| 类型标签、首字母缩写 | 7.1% | |

被 1,000 个以上文件共享的关键词占全部行数的 71.8%。

其他事实：

- 文件只增不缩。`auto_vacuum` 关闭；VACUUM 只在关闭正文索引之后、且磁盘剩余达到文件 2.5 倍时运行；FTS5 从不 optimize；「清理」只做 DELETE。所以文件停在历史峰值上，峰值里包括 09-26 之前每个文件一份的 base64 图标、开过的正文和向量、旧规则收录的行、重建时的暂存。
- 设置里的存储视图只统计主库，看不到 `search-index.db` 的构成。
- 收录不等于使用：dev profile 三周里有 1,297 个文件进过结果，打开过的只有 1 个；同期应用有 26 个、共 48 次。
- 同名且同大小的文件有 15,712 个副本（占 24%），多数来自 worktree 和多份检出。过滤策略本身没漏：`node_modules`、`.git`、隐藏目录、`~/Library` 下都是 0 个。
- 推算：只索引名字时每个文件 23–29 KB，8 GiB 上限约能放 30 万个文件。47.2 GB 相当于约 160 万个文件，或者文件更少但历史上开过正文索引。没拿到那台机器的库，这条是推测。

全量扫描时，新文件按每块最多 10 条写入，每块之后至少停 250 ms。2 万个新文件光节流就要 8 分钟以上，枚举耗时不到总耗时的千分之一。

### A. 存储

| ID | 事项 | 证据 | 前置与验收 |
| --- | --- | --- | --- |
| A1 | 正文只存一份 | 正文同时存在 `files.content`、FTS 内容表和 `content_chunks` | 先查清三份各自的读者（片段、向量、FTS）。FTS 改为 external content 需要迁移和重建。验收：同一组查询的结果与片段不变，体积下降 |
| A2 | 向量改为 Float32 二进制存储 | 768 维向量每行存成 16 KB 的 JSON，换成 Float32 是 3,072 字节 | 写入和读取两端同时改并迁移旧数据；语义召回 p50/p95 不回退 |
| A3 | 收缩 n-gram 关键词 | 已并入 A12，那里有 2026-10-20 的实测和读取路径 | — |
| A4 | VACUUM 门槛（已完成 10-21，见上方「空间回收」） | 要求空闲空间达到文件大小的 2.5 倍（19 GB），本机只有 14 GB，所以 1.27 GB 空闲页一直回收不了（冗余索引退役后是 1.69 GB）。用户侧的表现：「清理」只做 DELETE，47.2 GB 的那台机器清理几次文件都没变小 | 改为按「2 ×（文件 − 空闲页）+ 余量」计算，或一次性切到 `auto_vacuum = INCREMENTAL` 后用 `incremental_vacuum` 分批回收 |
| A5 | legacy（非 split）库里的冗余索引 | 在主线程 DROP 会卡住 UI，所以没处理 | split 默认开启，只影响回滚到 `=0` 的用户 |
| A6 | 索引满时正文索引每 30 秒撞一次 | 正文写入遇到 `SQLITE_FULL` 只暂停 30 秒，恢复条件是磁盘剩余 ≥ 3 GiB（`file-provider-content-capacity-service.ts`）。索引到上限而磁盘有空时会反复恢复、反复失败，设置页还报「磁盘空间不足」 | 索引到上限时正文索引保持暂停，提示说的是索引满而不是磁盘满 |

| A8 | 上限不计 `.corrupt` 隔离副本 | 损坏库会保留一份 `.corrupt`，最坏情况下占用是上限的两倍 | 决定超限时删掉副本还是计入上限 |
| A9 | legacy（非 split）模式没有上限 | 索引表在 `database.db` 里，不能整库删掉重建 | 只影响 `TUFF_DB_SEARCH_SPLIT_ENABLED=0` 的应急回退 |

| A11 | 不再给每个文件写路径类关键词（已完成 10-21） | 祖先目录分词 15.7%，路径短语 13.2%；FTS 的 `path` 列已经覆盖目录名匹配 | 目录名命中改由 FTS 计分（权重 0.3，原来精确关键词加成 0.45），先对一组查询比较排序 |

### E. 运行时（旁路发现）

| ID | 事项 | 证据 | 前置与验收 |
| --- | --- | --- | --- |
| E1 | 维护轮与 worker 空闲退出每分钟撞一次 | 维护轮做完后 60 秒再跑（`index-maintenance-runner.ts`），worker 空闲 60 秒退出（`idle-worker-shutdown.ts`），两者从同一次写入起算。隔离实例空闲时每分钟一条 `SEARCH_INDEX_WORKER_TERMINATION_UNCONFIRMED:pending`，250 ms 后重试并重建 worker | 会收敛，代价是日志噪音和每分钟一次 worker 重建。错开两个周期，或让维护请求等终止确认 |
| E2 | 扫描遇到 `SQLITE_BUSY` 会停住文件源一整个会话 | 除存储满以外的扫描失败都置 `initializationFailed`，health 变为 `error`，runtime 随后跳过这个源的全部监听事件和扫描；手动重建会先清空索引，扫描却被跳过（代码追踪，未实测） | 先实测复现。瞬时错误不应停住源，或者需要一条能解除 `error` 的路径 |
| E3 | 搜索之后退出要等满 8 秒 | 隔离实例从主窗口发一次 `core-box:search:query` 后退出，`search-engine-core` 的卸载会卡到 8 秒退出预算耗尽（`before-quit handlers timed out`）；等推送请求超时之后再退出也一样；不搜索时 2 秒退出。拆分前的代码同样复现 | 只用 IPC 发起的搜索复现过，真实 CoreBox 搜索是否同样触发还没确认（确认需要弹出 CoreBox 窗口）。从 `sessionRegistry.destroy()` 查起 |
| E4 | 用户加的索引路径在基础根之下时，目录规则照样生效 | 嵌套的根会并进外层的根（`resolveIndexedWatchRootSet`），macOS 的基础根是 home，所以 home 下用户加的路径都不会单独成根。扫描和监听对它照常套用目录规则（`node_modules`、项目里的 `build`、worktree），只有清理对「用户监控的路径」豁免。结果：用户没法靠加路径把这些目录收回来（代码追踪） | 先定产品语义：用户显式加的路径是否应当绕过目录规则。若是，扫描选项要能带上这些路径 |
| E5 | 维护片失败后每 250 ms 重试一次，没有退避 | `index-maintenance-runner.ts` 失败时记一条 warn，然后 250 ms 后重排。A10 的上限修正之前，旧行分散的满库每一片都撞满（探针用例复现），照这个节奏就是每 250 ms 一次失败和一条 warn，排在后面的孤儿清理也跑不到（代码追踪）。搬迁现在不会这样失败，其他持续失败的片仍会这样 | 失败时按次数退避，成功一片后复位 |
| E6 | A10 首次实测时主进程崩溃过一次 | 隔离实例启动健康检查后约 0.4 s，CrBrowserMain 线程在 JIT 代码里 SIGSEGV（minidump 手工解析）。之后 4 次启动没有复现，其中 2 次是由旧快照升级。转储留在本机，没有入库 | 再出现时对照这份转储；目前没有证据指向 A10 |

## 4. 验收原则

- 每项先给同机基线，再给改动后的数字；不引用上游 README 里的数字。
- 快照扫描和实时监听共享覆盖策略：根、深度、规范化、排除规则（[跨层指南 Mistake 9](../../../engineering/specs/guides/cross-layer-thinking-guide.md)）。
- 涉及 schema 或数据迁移的项，按[数据库写入契约](../../../engineering/specs/main-process/database-write-contracts.md)单独确认影响范围后再动。
